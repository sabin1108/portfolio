# 기술 선택과 설계 판단

**React SPA와 비교해 Next.js를 선택한 이유**

**React SPA로 구현하면 화면 외에 라우팅과 API 서버를 별도로 구성하고, 인증 흐름까지 연결해야 하는 부분** Next.js는 파일 기반 라우팅과 서버 API 기능을 함께 제공해, Better Auth·Prisma를 활용한 인증·DB 처리를 화면과 같은 구성 부분에 대해서 비교하면서 **여러 도구를 따로 조합하고 연결하는 부담을 줄일 수 있다고 판단해 Next.js를 선택했습니다.**

**같이 보이는 정보도 책임과 수명은 다르게 관리했습니다**
현재 화면의 위치, 보관할 작업 내용, 실제 실행 권한을 같은 상태로 취급하지 않고 역할에 맞게 나눴습니다.

| Better Auth · 계정 연결 정책의 관리 위치                                                                                                                                                                                      | Stepper · searchParams의 역할 분리                                                                                                                                                                                |
| :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **NextAuth/Supabase Auth·Better Auth**를 가입·복구·계정 연결 흐름으로 비교했습니다.<br><br>관리형 인증의 편의도 고려했지만, 모아에서는 여러 계정에 대한 연동을 위한 앱 코드와 Prisma 구조에서 함께 조정하기 위해 **Better Auth**를 선택했습니다. 대신 메일·OAuth 설정과 인증 코드 업데이트를 관리할 책임이 남았습니다. | 복사·이동 절차가 아래로 계속 쌓여 화면이 길어지고, 지금 해야 할 일을 찾기 어려웠습니다. 필요한 확인을 없애기보다 **Stepper**로 현재 단계의 작업을 중심에 두었습니다.<br><br>**searchParams**에는 단계와 초안 참조만 남기고, 실제 입력·계획은 별도로 보관했습니다. URL로 위치를 복원해도 현재 파일과 권한은 다시 확인하도록 했습니다. |

| 레고처럼 조합하는 컴포넌트와 공유 상태                                                                                                                              | 캐시의 범위와 갱신 기준                                                                                                                                                                                                                                                                    |
| :------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 목적지 탐색·경로 입력·새 항목 생성이 여러 작업에서 반복돼, **React 컴포넌트와 커스텀 훅**을 공통 부품처럼 조합했습니다. <br><br>화면 사이의 공유 상태는 **Context와 기존 저장소**에서 관리하고, 계정이 바뀌면 이전 상태를 분리했습니다. | **자주 바뀌지 않으면서 반복해서 조회되는 정보**를 재사용하기 위해, 설정 표시 정보에 **Next.js 캐시**를 적용했습니다. 현재 인증은 요청마다 확인하고, 표시 정보는 사용자·로그인별로 재사용하되 변경되면 갱신하도록 했습니다.<br><br>PDF는 **질문이 달라져도 원본이 같으면 추출한 본문은 동일하다**는 점을 고려해 **IndexedDB**에 보관하고 재사용했습니다. 현재 원본이 같은지 확인한 뒤 본문을 재사용하고, 처음 읽거나 내용이 바뀌면 다시 추출하도록 했습니다. |

# 핵심 기능 구현

| 폴더 연결과 자료 탐색 | 자료 질문과 대화 표시 |

| **File System Access API**로 사용자가 선택한 폴더를 연결하고, 폴더 목록·경로 이동·파일 선택을 구현했습니다.<br><br>불러오는 중·빈 폴더·권한 오류를 서로 다른 상태로 표시했습니다. 목적지 폴더를 읽는 동안에는 이전 목록을 유지하고, 새 목록이 준비되기 전에는 선택 확정을 막았습니다. | 선택한 자료의 발췌와 질문을 **Server Actions**로 전달하고, 답변에 표시된 출처를 통해 사용한 자료를 다시 확인하도록 연결했습니다.<br><br>일반 대화는 **SSE**로 받은 본문과 화면에 표시한 분량을 나눠 조금씩 보여주고, 중지·완료·오류 상태를 구분했습니다. 중지 뒤 늦게 도착한 응답은 현재 대화에 반영하지 않도록 했습니다. |

| 정리 계획과 단계별 실행 | 편집·저장과 복구 |
| :--- | :--- |
| **Stepper**로 목적지 선택·충돌 확인·실행·결과를 연결하고, **searchParams**와 별도 초안에서 현재 작업을 복원했습니다. 복원된 주소만으로 파일 작업을 다시 실행하지 않도록 했습니다.<br><br>최초 정리 요청과 후속 답변의 입력 상태를 나눠, 답변을 작성하는 동안 선택한 자료를 유지했습니다. 답변을 반영하면 이전 제안과 전송 동의를 초기화해 변경된 조건으로 다시 확인하도록 했습니다. | 텍스트·Markdown 문서를 기존 미리보기 안에서 편집하고, 수동·주기 저장으로 연결했습니다. 미저장 내용이 있으면 편집을 닫기 전에 확인하고, 저장에 실패하면 작성 중인 내용을 유지했습니다.<br><br>덮어쓰기는 기존 파일의 복구 사본을 확보한 뒤 별도 확인을 거치도록 했습니다. 보관 목록·상세 확인·복원 화면을 연결해 변경 이후에도 자료를 확인하고 복구할 수 있도록 했습니다. |

## 나뉘거나 합쳐져 도착하는 SSE 데이터를 처리하는 문제

네트워크에서 받은 조각을 바로 이벤트로 취급하지 않고, 완성된 이벤트를 구분해 처리했습니다.

**문제**

스트리밍 응답의 한 이벤트가 여러 번에 나뉘어 도착하거나, 여러 이벤트가 한 번에 도착할 수 있습니다. 한 번 읽은 데이터를 한 이벤트라고 가정하면 본문을 잘못 해석하거나 완료·오류 처리를 놓칠 수 있었습니다.

| 고민과 선택                                                                                                          | 해결 흐름                                                                                                                 |
| :-------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------- |
| 조각을 받을 때마다 바로 JSON으로 해석하는 대신 **수신 버퍼와 SSE 파서**를 뒀습니다. 전송 형식 해석과 대화 상태 변경을 나눠, 불완전한 데이터가 화면 상태에 직접 들어가지 않게 했습니다. | 받은 문자열을 버퍼에 붙이고 이벤트 구분자가 완성된 부분만 꺼냅니다. 남은 조각은 다음 수신까지 보관합니다. 완성된 이벤트의 형식·요청 세대·순서를 확인한 뒤 본문, 완료, 오류에 맞는 상태 변경을 수행합니다. |
| **검증**<br>이벤트가 분할되거나 여러 개 합쳐진 입력, 완료·오류·취소 경로를 합성 스트림으로 검사했습니다. 파싱한 본문이 실제 표시 흐름까지 이어지는지도 관련 브라우저 검사로 확인했습니다.   | **결과**<br>네트워크 수신 단위와 앱의 이벤트 단위를 구분했습니다. 수신 형식이 달라져도 완성된 이벤트만 상태에 적용하고, 본문 표시와 전송 오류 처리를 각각 추적할 수 있게 했습니다.            |

## 응답 완료 시 남은 글자가 한꺼번에 표시되는 문제

서버 응답이 끝난 시점과, 사용자가 답변을 모두 본 시점을 구분했습니다.

**문제**

챗봇 장문의 답변을 순차적으로 표시하는 것이 아닌, 3~4줄 정도의 내용을 한꺼번에 나타나는 현상을 발견했습니다. 이는 내용이 애매하게 많은 내용을 한번에 보내게 되면 사용자가 사용하는데 있어 어색함과 불편함을 가지게 될거라 판단하여, 서버의 응답 수신이 끝나더라도 남은 내용을 순차적으로 표시하도록 수정했습니다.

| 고민과 선택                                                                                                                  | 해결 흐름                                                                                                                                              |
| :---------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------- |
| 한번에 모든 정보를 쏟는 방식이 정보의 과부화와 사용성에 저하를 주게 됩니다. **받은 본문과 화면에 공개한 길이를 분리**하고, 완료 이벤트 뒤에도 남은 내용을 화면 갱신 주기에 맞춰 이어서 표시하도록 했습니다. | 텍스트를 받으면 수신 본문에 누적합니다. requestAnimationFrame에 맞춰 표시 길이를 늘리고, 수신이 끝나도 표시가 전체 길이를 따라잡을 때까지 공개를 계속합니다. 중지·오류·계정 변경에는 남은 표시 작업을 정리합니다.                 |
| **검증**<br>                                                                                                              | **결과**<br>완료 이벤트가 와도 남은 본문이 한꺼번에 나타나는 흐름을 줄였습니다. 사용자가 웹을 이용하면서 필요한 결과를 한번에 받는 것과 순차적으로 글이 작성되는 효과와 글이 배열되는 효과를 보여주는 것에 UX 적 차이가 크다는 것을 확인하게 되었습니다. |

## 폴더 이동 중 입력창과 목록이 깜빡이는 문제

## 공통 폼의 식별값 충돌로 경로 입력이 잘못 연결되는 문제

폴더를 찾아가는 입력창과 새 항목을 만드는 입력창을 서로 구분하도록 수정했습니다.

**문제**

목적지 선택 화면에는 **기존 폴더를 찾아가기 위한 경로 입력창**과 **새 파일·폴더의 이름을 입력하는 생성 폼**이 있었습니다. 두 폼을 배치하는 상위 화면에서 현재 폴더 경로만 React key로 지정해, 역할이 다른 두 폼에 같은 값이 들어갔습니다.
React key는 화면의 부품을 구분하는 이름표입니다. 이 이름표가 겹친 상태에서 하위 폴더로 이동하면 입력창이 정상적으로 표시되지 않는 오류가 발생했습니다.

| 고민과 선택                                                                                                                            | 해결 흐름                                                                                                            |
| :-------------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------- |
| 두 폼은 같은 폴더 위치를 사용하지만, 하나는 **기존 위치로 이동**하고 다른 하나는 **새 항목을 생성**합니다. 현재 경로만으로는 서로 다른 두 폼을 구분할 수 없으므로, key에 각 폼의 역할도 포함해야 한다고 판단했습니다. | 기존 경로값 앞에 **경로 입력용·새 항목 생성용이라는 역할을 추가**해 서로 다른 key를 지정했습니다. 같은 폴더를 사용하더라도 두 폼의 이름표는 겹치지 않도록 수정했습니다.              |
| **검증**<br>실제 브라우저에서 하위 폴더에 처음 들어갈 때 입력창 개수 검사가 실패하는 것을 확인했습니다. 수정 후 **폴더 왕복 20회 동안 총 40차례** 입력창 개수와 표시 경로를 검사했습니다.                | **결과**<br>검사한 모든 위치에서 각 폼이 의도한 경로가 맞는지 확인했습니다. 공통 부품을 사용할 때는 사용하는 데이터뿐 아니라 **화면 안에서 맡은 역할도 구분해야 한다는 점**을 확인했습니다. |
